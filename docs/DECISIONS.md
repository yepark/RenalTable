# 아키텍처 결정 기록

큰 결정은 `결정 / 대안 / 가정·트레이드오프 / 재검토 조건`으로 기록한다.

## ADR-001 모듈형 모놀리스

- 상태/날짜: 채택, 2026-11-01
- 결정: 하나의 Next.js 앱 안에서 foods, recipes, profile, planner, guide 모듈을 분리한다.
- 대안: 마이크로서비스, 단순 페이지별 혼합 구조.
- 이유: 작은 팀/MVP에서 배포·관찰 비용을 줄이면서 도메인 경계와 테스트 가능성을 유지한다.
- 트레이드오프: 모듈 경계를 lint와 review로 지켜야 한다.
- 재검토: 독립 배포/스케일 요구가 실제 측정으로 나타날 때.

## ADR-002 Next.js 16 App Router와 Node 24 LTS

- 상태/날짜: 채택, 2026-11-01
- 결정: Next.js 16 Active LTS, Node 24 LTS, 호환 React 19/TypeScript 5.9를 Phase 1 기준으로 한다.
- 대안: Next 15 Maintenance LTS, Node 26 Current/LTS 전환 직후, Vite SPA.
- 이유: 공식 지원 중인 안정 계열, SSR/정적 페이지/API를 한 앱에 구성, 운영 LTS 선호.
- 트레이드오프: 최신 React/Next 보안 패치를 계속 추적해야 하며 정확한 patch는 초기화 당일 확정한다.
- 재검토: Phase 1 당일 지원 정책 변경, Next 16 호환성 결함, 배포 플랫폼 제약.

## ADR-003 PostgreSQL + Drizzle

- 상태/날짜: 채택, 2026-11-01
- 결정: 관계형 데이터는 PostgreSQL, schema/query/migration은 Drizzle과 리뷰 가능한 SQL을 사용한다.
- 대안: Prisma, raw SQL, document DB.
- 이유: 강한 FK/check/transaction, SQL 중심 ETL, 얇은 타입 안전 계층.
- 트레이드오프: repository와 복잡 쿼리 설계를 팀이 직접 책임진다.
- 재검토: Phase 2 spike에서 migration/driver 안정성 또는 팀 생산성이 기준 미달일 때.

## ADR-004 Supabase는 제공자 후보, 결합점 아님

- 상태/날짜: 조건부 채택, 2026-11-01
- 결정: PostgreSQL 표준 연결을 유지하고 Supabase는 Phase 2 호스팅 후보로만 둔다.
- 대안: 로컬/자체 PostgreSQL, Neon, Prisma Postgres 등.
- 이유: 무료 시작과 관리 편의가 있으나 Free의 용량·휴면·운영 제약이 있다.
- 트레이드오프: 공급자 전용 기능을 초기에는 활용하지 않는다.
- 재검토: 데이터 크기 산정, 가용성 요구, 비용/약관 검토 후 외부 연결 승인 시.

## ADR-005 건강 프로필과 식단은 로컬 우선

- 상태/날짜: 채택, 2026-11-01
- 결정: 계정 없이 프로필, 목표, 식단, 체크 상태를 브라우저에만 저장한다.
- 대안: 익명 서버 세션, 계정 기반 동기화.
- 이유: 건강정보 수집과 침해 범위를 줄이고 MVP 복잡도를 낮춘다.
- 트레이드오프: 공동 기기 노출, 기기 간 동기화 불가, 브라우저 삭제 시 손실.
- 재검토: 사용자 조사에서 동기화 요구가 높고 개인정보 영향평가/인증 설계가 승인될 때.

## ADR-006 사용자 입력 목표만 비교

- 상태/날짜: 채택, 2026-11-01
- 결정: 앱이 질환/투석 방식만으로 영양 목표를 생성하지 않는다. 사용자가 의료진에게 받은 목표를 입력한 경우에만 수치 비교한다.
- 대안: 지침 기반 기본 목표, AI 개인화 목표.
- 이유: 개인 임상 상태 차이와 영양실조 위험을 일반 규칙으로 덮지 않기 위해서다.
- 트레이드오프: 목표 없는 사용자는 일반 정보만 받고 추천 범위가 제한된다.
- 재검토: 규제·임상 검토를 거친 별도 의료기기 수준 기능이 명시적으로 승인될 때.

## ADR-007 누락값의 명시적 전파

- 상태/날짜: 채택, 2026-11-01
- 결정: 영양값은 amount와 status를 가지며 null을 0으로 치환하지 않는다. 부분 합계는 목표 충족 판정에 사용하지 않는다.
- 대안: 누락을 0/평균값으로 대체, 불완전 행 제외.
- 이유: 특히 칼륨·인 누락이 거짓 저함량으로 보이는 위험을 막는다.
- 트레이드오프: 평가 가능한 레시피 수가 줄 수 있다.
- 재검토: 검증된 보간 모델과 임상 검토가 마련되더라도 “추정값”을 별도 상태로 추가하는 방식만 검토한다.

## ADR-008 규칙 기반 추천과 생성형 AI 분리

- 상태/날짜: 채택, 2026-11-01
- 결정: 필터·비교·정렬은 버전 있는 순수 함수로 구현하고 설명은 결정적 템플릿을 사용한다.
- 대안: LLM이 메뉴/설명을 실시간 생성.
- 이유: 재현성, 출처 추적, 테스트 가능성, 의료적 환각 방지.
- 트레이드오프: 설명 다양성과 메뉴 폭이 제한된다.
- 재검토: AI 출력이 검토 queue에만 들어가고 자동 게시되지 않는 관리자 보조 기능을 별도 설계할 때.

## ADR-009 공공데이터는 staged ETL 후 게시

- 상태/날짜: 채택, 2026-11-01
- 결정: 사용자 요청 시 외부 API를 호출하지 않고 raw→validate→normalize→review→publish pipeline을 거친다.
- 대안: 실시간 API proxy, 수동 CSV 직접 import.
- 이유: 변경·중복·누락을 검증하고 출처/버전을 재현하기 위해서다.
- 트레이드오프: 데이터 최신성이 즉시 반영되지 않고 운영 작업이 필요하다.
- 재검토: 공식 webhook/version contract와 자동 품질 기준이 충분히 안정화될 때.

## ADR-010 배포와 게시의 사람 승인

- 상태/날짜: 채택, 2026-11-01
- 결정: 외부 데이터 운영 반영, 의료 콘텐츠 공개, 외부 서비스 연결, 프로덕션 배포를 자동 완료하지 않는다.
- 대안: main merge 자동 배포/게시.
- 이유: 의료정보, 라이선스, 비용, 개인정보 책임이 발생한다.
- 트레이드오프: 출시 속도가 느려지고 승인 담당이 필요하다.
- 재검토: 역할·감사·rollback이 갖춰져 승인 workflow 자체를 자동화할 때도 최종 책임자 승인은 유지한다.

## ADR-011 접근성 목표는 WCAG 2.2 AA

- 상태/날짜: 채택, 2026-11-01
- 결정: 반응형 모든 변형에서 WCAG 2.2 AA를 목표로 자동+수동 검증한다.
- 대안: 자동 axe 통과만 사용, WCAG 2.1 기준.
- 이유: 큰 글씨, 키보드, 명확한 오류, 터치 목표는 핵심 사용자에게 직접적인 품질이다.
- 트레이드오프: 컴포넌트/수동 검증 비용이 늘어난다.
- 재검토: 목표를 낮추는 재검토는 하지 않으며 새로운 표준/국내 법적 기준은 상향 반영한다.

## ADR-012 배포 플랫폼은 보류

- 상태/날짜: 보류, 2026-11-01
- 결정: Vercel을 기술 후보로 두되 계정 연결과 배포는 하지 않는다.
- 대안: Vercel Pro, 다른 무료/유료 호스팅, 자체 운영.
- 이유: Vercel Hobby는 개인·비상업 용도 조건이 있고 공개 무료 서비스의 운영 주체/트래픽이 아직 정해지지 않았다.
- 재검토: Phase 6에서 운영 주체, 예산, 가용성, 개인정보, 약관을 검토하고 사용자 승인을 받을 때.

## ADR-013 사용자 무료와 월 0원 인프라

- 상태/날짜: 채택, 2026-11-01
- 결정: 사용자는 모든 MVP 기능을 무료로 이용하며, 초기 인프라 비용은 월 0원을 유지한다. 자동 과금되는 플랜 전환은 하지 않는다.
- 대안: 광고 기반 무료 서비스, 유료 구독, 초기부터 유료 호스팅.
- 이유: 프로젝트의 공익적 목표와 사용자의 명시적 무료 운영 요구사항을 지키기 위해서다.
- 구현 방향: 비공개 GitHub 저장소를 유지하는 동안 개인·비상업 조건의 Vercel Hobby와 Supabase Free 한도 안에서 운영한다. 목표 기본 주소는 가용할 경우 `https://renaltable.vercel.app`이다.
- 트레이드오프: 무료 한도 초과나 휴면 정책으로 서비스가 일시 중지될 수 있으며 SLA를 제공할 수 없다. GitHub Pages는 GitHub Free에서 공개 저장소가 필요하므로 현재 비공개 저장소에는 사용하지 않는다.
- 재검토: 트래픽이 무료 한도를 넘거나 운영 주체가 개인·비상업 범위를 벗어날 때. 재검토 시에도 유료 전환 전 사용자 승인을 받는다.
